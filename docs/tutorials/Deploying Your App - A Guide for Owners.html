How a change gets from an idea to your live app

Your AI agents do the technical work of testing and releasing the HTI Research Admin app. Your job is to decide: you read short proposals in Buzz, try the app in a safe test copy, and reply approve when you are happy.

Meet the five players. Their colours are used throughout this guide.

You

You, the owner

Decides and approves

Asks for changes, checks the test copy, and replies approve to proposals. Nothing important happens without you.

C

Cody

Developer agent · UAT

Changes the app, sets it up, deploys it to the test copy (UAT) and fixes problems found there.

O

Oppo

Operations agent · production

Releases the tested version to the live app and watches it. Until Oppo exists, Cody can do this too.

⚙

The system

Team Builder manager

Does the actual installing, runs safety checks, keeps a record of every release, and refuses anything you did not approve.

IT

Your operator

Server administrator

Stores passwords and other secrets on the server, and keeps it running. Secrets never go into chat.

The big picture

The journey of a change

Every change travels the same road. Click each stop to see what happens there and what, if anything, you need to do.

Cody makes the change

You describe what you want in Cody's channel. Cody edits the app's code and opens a pull request, a proposed code change that someone reviews before it is accepted.

Once the change is reviewed and accepted (“merged”), it starts its journey automatically.

Your partDescribe the change. If you are the reviewer, accept the pull request on GitHub when Cody says it is ready.

A release is built and tested

A robot on GitHub runs the app's tests and packages the app into a sealed, numbered release, for example ci-37255024251-1. A release never changes after it is built, so what you test is exactly what goes live.

Your partNothing. This takes about 5–10 minutes.

The release arrives on your server

Every two minutes the system looks for new releases, downloads them and checks they are genuine. While it works it shows importing; when finished, the release appears in the list.

It is normal for this to take a few minutes after GitHub finishes. Arriving on the server does not install anything yet.

Your partNothing. If Cody says the release is missing, wait a few minutes.

Cody installs it on the test copy (UAT)

UAT is a private copy of the app with its own copy of the data. Cody prepares an exact plan (“install release X with settings Y”) and posts it as a proposal in Buzz.

You reply approve to that proposal. Cody then installs it and reports when the system's health checks pass.

Your partRead the proposal and reply approve directly to it.

You try the test copy

Open UAT in your browser and use the app the way your users would: sign in, open the pages that changed, check the numbers look right.

A green health check only means the app started. Whether it does the right thing is for you to judge.

Your partTest it. Tell Cody about anything wrong; the fix goes round the same journey again.

The same release goes live

When UAT is good, ask Oppo (or Cody) to release the same release number to production. Another proposal appears; you approve it; the live app is updated and checked.

If something goes wrong, the system puts the previous version back automatically. Your data is never rolled back or deleted by a release.

Your partApprove the production proposal, then do a quick check of the live app.

Later, this can become automatic. Once you trust the process, you can approve a “release policy” once. After that, every accepted change goes through UAT checks and into production on its own, and you are only asked when a real decision is needed. See Part C of the walkthrough.

Step by step

The full process, one step at a time

Part A is done once per app. Part B is what you do for every change. Part C is optional automation. Use the buttons or your ← → keys.

YouCOA (team manager agent)

A1. Give Cody permission to handle releases

New agents can't touch releases. You allow it once, through the Chief of Agents (COA), the agent that manages your team.

Do thisIn the Office of COA channel, send:
Office of COAMake Cody a release agent.

COA posts a proposal describing the change. Reply approve to it, either as a reply to that exact message or by tapping Reply on it and typing approve.

You only do this once. If you later add Oppo, the same works for Oppo.

What it looks like

Chief of Agents ProposalProposed team changes: make Cody a release agent. Reply approve to this message.

YouCody

A2. Ask Cody to set the app up

Cody reads the app's code and works out everything the server needs: what to run, which settings to use, which database to connect to, who runs UAT and who runs production.

Do thisIn Cody's channel (Platform Engineering), send:
Platform Engineering@Cody Set up hti-research-admin for UAT and production using your release tools. You operate UAT; production is run by Oppo (or by you until Oppo exists). Propose the setup for my approval, then tell me which secrets are missing.

Cody replies with one proposal listing everything. Read the checklist on the right before you approve it.

Before you approve, check
  • It names the right app and both environments (UAT and production).
  • UAT and production use different databases, unless you have decided otherwise.
  • The right agents get access: Cody for UAT, Oppo or Cody for production.
  • No passwords appear in it. Secrets are only ever named, never shown.

Not sure? Ask Cody in plain words, e.g. “Which database will UAT use?” Nothing happens until you approve.

CodyYouOperator

A3. Hand the secrets to your operator, not to chat

After setup, Cody lists the secrets the app still needs: database passwords, a login file and so on. Agents never ask for the values, and you must never paste them into Buzz.

Do thisForward Cody's list to your operator, together with where the real values are kept (password manager, existing server). The operator stores each one on the server.

When the operator says it's done, tell Cody:

Platform Engineering@Cody The secrets are stored. Please run the pre-flight check for UAT and tell me what is still missing.

If a secret was ever pasted in chat, treat it as leaked: ask the operator to change that password.

For the operator: storing one secret

On the server, as the installation owner, for each secret name Cody lists (example: mysql-password for UAT):

umask 077
echo '{"action":"credential","application":"hti-research-admin","environment":"staging","id":"mysql-password"}' > mysql-password.json
team-builder deployment mysql-password.json --secret-file /path/to/the/secret

UAT is called staging in commands. Delete the plaintext file afterwards. Full details: docs/application-deployment-guide.md.

Typical list from Cody
CodyStill missing for UAT: mysql-password, auth-db-password, crm-report-db-password, gateway-token-secret, users-yaml (login file). Please have them stored on the host; I never need the values.
OperatorCody

A4. Make sure the test copy has its own data

UAT should use a copy of your data, so testing can never damage the real thing. For HTI, the operator created a UAT database on the server, copied from production, and Cody connected the app to it.

Some parts of the app use other systems, such as the login directory or the report database. If a page fails because one of those isn't connected yet, that's an infrastructure task for the operator, not something you need to fix.

Do thisDecide whether UAT may use any production systems directly. The safe default is no: UAT gets copies or read-only access.
Why a separate copy matters

In UAT, people click buttons to try things out. If UAT shared the live database, a test edit would change real records.

With a copy, the worst case is resetting UAT, and your users never notice.

YouCody

B1. Ask for a change

Describe what you want in plain language, as you would to a colleague. Mention Cody with @Cody so the message reaches it.

Platform Engineering@Cody On the analyst interactions page, add a filter for the last 30 days. Open a pull request when it's ready and tell me how to review it.

Cody changes the code, runs the tests, and opens a pull request. Someone, often you, accepts (“merges”) it on GitHub. From that moment the change is on its way.

Tips for good requests
  • Say what you want and why, not how to code it.
  • Give an example: “the March numbers should show 42”.
  • Reply in the same thread to add details.
System

B2. Wait for the release to arrive

After the change is accepted, GitHub builds and tests a release (5–10 minutes). The server then picks it up within a few minutes and verifies it.

You don't need to do anything. If you ask Cody too early, it may say the release is importing. That means “nearly there”, not “broken”.

Only stale (no successful check for 10 minutes) or failed means something needs attention, and Cody will say so.

Where a release is
CodyRelease ci-37255024251-1 is importing (started 2 minutes ago). I'll propose the UAT deployment as soon as it's registered.
YouCodySystem

B3. Approve the UAT deployment

Platform Engineering@Cody Deploy the latest release to UAT and tell me when it's healthy.

Cody posts a proposal: the exact release number, environment (staging = UAT) and settings. Reply approve to that message. Use the Reply button on it, then type just approve.

The system then runs safety checks, installs the release, and waits until the app reports healthy. Cody tells you when it has succeeded.

Queued or running is not finished. Wait for succeeded. If installation fails, the previous version is put back automatically.

Reading a deployment proposal
Cody ProposalDeploy release ci-37255024251-1 (commit a666a0d) to staging with profile uat-v3. No database migrations.
  • staging means UAT. production means live.
  • The release number is the one you expect.
  • “No database migrations” = your data's structure is untouched.
You

B4. Try the test copy yourself

Open UAT in your browser and sign in with your UAT account. Check what changed and a few things that should not have changed.

  • You can sign in.
  • The changed page works as you asked.
  • Important numbers match what you expect.
  • Nothing else looks broken.

Found a problem? Describe it to Cody with the page name and what you saw. The fix travels the same road: change → release → UAT.

How to open UAT (HTI)

UAT is only reachable through a secure connection to the server. Your operator can set this up once on your computer; afterwards, keep this running in a Terminal window:

ssh -N -L 18502:127.0.0.1:18502 ubuntu@sandbox2

Then open http://127.0.0.1:18502 in your browser. Your UAT password is separate from production.

When you are happy with UAT, send the same release number live. Never ask for “the latest”, because a newer release may have arrived that you haven't tested.

Production channel@Oppo UAT passed for release ci-37255024251-1. Deploy that same release to production and report when it's healthy.

Approve Oppo's proposal the same way. Then open the live app and do a quick check.

UAT approval does not approve production. Each environment needs its own approve.

If the live app has a problem

Approve it, and the previous version is back within minutes.

YouCody

C1. Approve a release policy, once

Once the manual process has worked a few times, you can let it run on its own. Cody writes automatic acceptance checks (read-only tests) and proposes a release policy: the agreed rules for when a release may go to UAT and then production.

Platform Engineering@Cody Propose an enabled release policy for hti-research-admin: run your acceptance checks in UAT and production, notify the production channel, and let the production agent roll back if production checks fail.

Read it carefully. Approving it means routine releases no longer need your approve.

What you're agreeing to
  • Every accepted change is installed in UAT and checked automatically.
  • Only if UAT checks pass does the same release go live.
  • If live checks fail, the previous version can be restored.
  • You can pause the policy at any time by asking Cody.
SystemCodyOppoYou, only when needed

C2. Life with automatic releases

From now on: change accepted → release built → UAT installed and checked → live installed and checked. You see progress in Mission Control → Deployments and short notices in the production channel.

If a step is blocked, the responsible agent is notified and investigates. You're only asked for things only you can provide:

  • A missing secret: the message includes exactly what to give your operator.
  • A decision outside the agreed rules, such as a database change.

You still test UAT whenever you like. Automatic checks catch breakage, but they don't judge whether a feature is what you wanted.

A typical notice
CodyAutomatic release ci-37301122334-1: UAT and production checks passed. Live app updated at 14:32.
OppoProduction check “reports-load” failed after release ci-37301122334-1. Previous version restored; investigating with Cody.

Remember

Five golden rules

RULE 1

Reply “approve” to the exact proposal

Use Reply on the proposal message itself. A new message, or a reply to a summary, doesn't count.

RULE 2

Never paste secrets into chat

Passwords go to your operator, who stores them on the server. Agents never need the values.

RULE 3

UAT first, then production

Every change is tried in the test copy before it goes live. Each environment needs its own approve.

RULE 4

Same release number in production

Release exactly what you tested, by its number, never “the latest”.

RULE 5

“Queued” is not “done”

Wait for succeeded. Agents report when the health checks pass.

AND

When unsure, ask in plain words

“What will this change?” or “Is this safe?” are good questions. Nothing happens without your approval.

Glossary

Words you will see

UAT / staging
The private test copy of the app, with its own copy of the data. “staging” is its technical name.
Production
The live app your users work in.
Release
A sealed, numbered version of the app (e.g. ci-37255024251-1) that never changes after it's built.
Proposal
A frozen description of exactly what an agent wants to do. It only happens if you reply approve to it.
Pull request
A proposed code change, reviewed before it's accepted (“merged”) into the app.
Pre-flight check
The system's safety check before installing: are all settings, secrets and connections in place?
Health check
An automatic “is the app up and answering?” test after installing. It doesn't prove features are correct.
Rollback
Putting the previous release back. It restores the app, not the data.
Release policy
Rules you approve once so routine releases go through UAT and production automatically.
Mission Control
The read-only dashboard showing agents, releases, deployments and their status.
Operator
The person who administers the server and stores secrets.
Secret
Anything that grants access: passwords, tokens, login files. Never shared in chat.
